# Release Notes — 0.19.5

## Changes

- **`pipelines:` is now reload-safe on `/cd`, `/new`, `/model`, `/load`.** The previous `PipelineSet` was built once at boot and every reload path warned `⚠ pipelines change ignored — restart to apply.` The set is now rebuilt inside `reload_session_config` from the fresh config and the fresh registry, after the skill re-scan (so a role's `skills:` filter is validated against the *new* repo's skills) and before `adopt_reloaded` (so it still has `&fresh`). A bad `pipelines:` block warns and keeps the previous set; the rest of the config is still adopted. A pipeline selection that no longer resolves in the new set is dropped with a warning; nothing is auto-selected (a local config declaring teams makes them *available*, never *active*).
- **Headline behaviour change:** `/cd` now adopts the target directory's *entire* `.peakbot/config.yaml` — `providers:` (including `base_url`), `tools:`, `bash.env`, `timeouts`, persona, *and* `pipelines:`. This was already true if you started PeakBot in that repo, but `cd`-ing into a freshly cloned repo now picks up its overrides the same way. This also fixes a load-bearing bug: the per-repo config loader and the skill re-scan were both reading the *process* cwd, which never moves, so they always re-read the OLD repo's config/skills on `/cd`. `session_cwd` is now passed explicitly everywhere post-boot. Loud release-note because if you `cd` into a cloned repo and it has a different `providers:` block, you will silently be on a different wire.
- **Frontend:** `RELOAD_SAFE_KEYS` (the wizard's restart-impact classifier) now lists `"pipelines"`; legacy `"pipeline"` stays boot-only. The `Review` step derives its split from `classifyChange`, so no other change there.
