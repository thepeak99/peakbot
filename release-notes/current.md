# Release Notes (Working Draft)

This file is the working draft for the next release. When a version is tagged, this file is renamed to `<version>.md` and a new empty `current.md` is created.

## Changes

### Cloud Mode

- **⚠ Update every linked device together.** The link between two of your devices moves to a new cloud pipe version, and an updated device and an older one cannot open sessions to each other: requests between a mixed pair fail until the second device is updated too. Nothing else needs to change — the relay needs no update and no data is migrated, so device identities, the device chain, enrollments and conversations are untouched; rolling back is safe too, as long as every device rolls back with it.
- **Two computers can now use each other in both directions, even when a stream is already open.** Once a cloud session exists, either side can open its own requests on it — ask a computer for its profiles or open a conversation while it already holds one to you. Before, only the device that started the session could ask for anything, so the other direction failed until the session was re-established. Each direction keeps its own stream, and a reset or failure on one side no longer disturbs the other side's open streams. A device that cannot serve requests at all (a phone with no local profiles) now refuses them at once, while its own requests keep working.

### Vector DB: universal v2 + git merge

- **Every vector store is v2.** A store's behavior is derived from where the DB file lives: inside a git repository → clone-portable repo-relative document IDs, gitignore-aware discovery, and automatic reconcile (pending marker, HEAD change, or DB stamp) whether the file is tracked or gitignored; outside any repository → the same v2 record (fingerprint + manifest) with absolute local IDs, plain discovery, and no state. Both store kinds use the same format; git merge support is a capability of the repo-anchored contract, not a separate DB mode.
- **Committing the DB is opt-in.** `.peakbot/vectors.db` and the local reconcile state `.peakbot/vectors.db.peakbot/` are untracked by default. To make the DB travel, un-ignore the DB file, add `.peakbot/vectors.db merge=peakbot-vectors` to a repo-root `.gitattributes`, and run `git config merge.peakbot-vectors.driver 'peakbot vectors merge-driver %O %A %B %P'` once per clone — use the full path to the binary if `peakbot` isn't on your `PATH`.
- **Merges run offline and resolve deterministically.** A merge invokes the driver, which reads no config, never touches the keyring, and never embeds or reaches the network: overlapping changes keep this branch's rows, newly added documents are adopted, the manifest is unioned, and a store built with a different model is never mixed in.
- **No sync command — the store keeps itself fresh.** After any merge (and whenever a clone's local state is missing, HEAD changes, or the DB file is replaced on disk) the next user or background turn reconciles automatically, and `doc_index`/`doc_search` reconcile before reading. Directory discovery uses git, so `.gitignore`d paths (build output, secrets) are never embedded. Reconcile re-embeds only changed files, reuses hashes for unchanged ones, and prunes deleted files; a failed embeddings request leaves the repair marker set so the next turn retries. Searching a stale or unusable store errors instead of returning possibly-wrong matches.
- **What it doesn't do.** A populated v1 store is temporary read-only compatibility only: search works, but `doc_index`/any write returns `MigrationRequired`; PR2 migrates, and both PRs ship in the same release. A zero-row empty store is adopted into v2 on its first write. Relocating a DB across the repo/local boundary reads existing rows but refuses writes. No git hooks are required. Don't merge while a PeakBot session is actively indexing (any OS); on Windows, close **every** PeakBot instance first, because replacing an open file can fail outright and abort the merge.

### Caching

- **Chats open faster on every device, and remote chats keep working while offline.** Each device now keeps a shared local cache of conversations: the 100 most recent across every linked machine, plus any chats you've opened. While online, the chat list stays current without polling, and opening a chat fetches only what's new — new messages arrive as a small suffix, with a moving anchor refreshed every 10 new rows so the cache never drifts. Cached chats stay readable offline, and when a computer or device is unlinked, its cached chats are automatically cleared.
### Fixes
- Mobile: pictures from agent `view_image` tool results now appear when tapping the tool result open, tap image for full-screen; desktop unchanged.
- Cloud: the phone now lists every linked computer separately — with its own device name and host color — even when several share the same profile name.
- Cloud: first-device, revoke, and sign-out confirm dialogs now close when the request completes; failures are shown in the pane.
- Cloud: first-device setup copy now explains the permanent device history and that every device has equal approval rights; the trust-mismatch banner no longer claims the root device changed.
- Cloud: requesting something from a device whose relay connection is gone now fails at once (its open streams are reset and pending requests answered) instead of waiting; a handshake that never completes is retired after 30 seconds instead of holding the session for a day, so a request to a device that has not been updated fails within 30 seconds instead of hanging.
- **Shifu icon refresh and Copy code.** The mobile Shifu app and conversation header now use the new Shifu logo, sub-agent tool rows on mobile now show the sub-agent's attribution, fenced code blocks in messages now carry a Copy code button on mobile and desktop, and the desktop executable, window, and tray use the new black-and-white Shifu icon.
