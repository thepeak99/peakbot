# Release Notes (Working Draft)

This file is the working draft for the next release. When a version is tagged, this file is renamed to `<version>.md` and a new empty `current.md` is created.

## Changes

- Added `peakbot --web` (Phase 0): the binary now embeds a React + Vite + Tailwind web UI via `rust-embed`, served on a fixed loopback port by a small axum server. The bundle is a **full static mock** of the finished UI — top bar with model/tokens/cost, welcome banner, a transcript rendering every message role (user, agent, tool call, tool result, summary, background), a side rail with session stats, a context-usage meter, todo and background-process panels, a foreground `bash` output strip, and the composer — all driven by hardcoded mock data. No WebSocket or live state yet; that is Phase 1.
- New `make web` target builds the SPA (`npm install && npm run build`) so `cargo run -- --web` shows the real UI. The four release Dockerfiles now run the same Node stage, so release binaries ship the real bundle too.
- `build.rs` writes a self-explaining stub `web/dist/index.html` when `make web` hasn't been run, so a node-free `cargo build` still produces a working binary that tells the operator what to do. CI installs Node 22 and runs the real frontend gate (`npm ci && lint && typecheck && build`, where `lint` is ESLint) before the Rust checks.
- `peakbot --web` (Phase 1): the web UI is now **live**. A `GET /ws` WebSocket endpoint drives a fresh, independent agent session per browser connection — each tab is its own transcript, todo, stats, and context; closing it tears the session down (including any background PTY children). The frontend connects over WebSocket, renders live `AppState`, sends messages, streams the "working…" spinner and Stop button, and answers `/help`, `/stats`, and other slash commands. Agent replies, compaction summaries, and tool results render as GitHub-flavoured Markdown (react-markdown + remark-gfm) with syntax-highlighted code (rehype-highlight); user input and system lines stay literal, and no raw HTML is rendered.
- Introduced a **session factory** (`create_session`) shared by every View: the TUI and stdio Views build one session; the web UI builds one per connection. The stdio/web wire protocol was extracted into a single shared `src/ui/wire.rs` so both transports change together. No new backend routes or `UiAction` variants — the web UI is a render of the existing `AppState` plus the existing inbound actions.
- `peakbot --web` (Phase 2): commands, models, and conversations are now interactive. A **model switcher** dropdown in the top bar lists the model registry and switches with one click; a **conversations picker** in the side rail lists saved conversations (numbered, by title) and loads one on click — both confirm first when they would clear a non-empty transcript. The composer gained a **slash-command palette**: type `/` to filter commands (↑/↓ + Enter/Tab to pick, Esc to dismiss). Session stats and the context-usage meter were already live from Phase 1. The command list is served by a new read-only `GET /commands` endpoint sourced from `builtin_commands()` (the single source of truth — no duplicated list, no WebSocket-protocol change).
- The web conversations picker now shows a spinner + "Loading conversations…" while the async list is in flight, instead of flashing "No saved conversations." before the data lands.
- Fixed the web UI welcome banner going stale after a `/model` switch: it now updates the provider, model, and max-tokens shown to match the model just switched to (previously it kept displaying the boot model even though the model selector and status bar had already changed). The TUI's static banner is unaffected.
- Added a `make dev` target for a web-UI hot-reload loop: it runs the backend under `cargo watch` (`127.0.0.1:7823`) and the Vite dev server (`localhost:5173`) together. Open `localhost:5173` — Vite serves the app with HMR and proxies `/ws` to the backend (new proxy entry in `web/vite.config.ts`). Web-source edits hot-swap in <1s; Rust edits rebuild+restart the backend (dropping the WS session, which the browser reconnects). No Rust code paths changed — the production `--web` build is unchanged. Requires `cargo install cargo-watch` and Node.js 22+; documented in README and `agents.md`.
- `peakbot --web` (Phase 3): you can now **attach images** in the browser. Paste an image from the clipboard or drag-and-drop a file onto the composer — attachments show as removable thumbnails above the input and are sent alongside your message. Over-size files (>10 MB) and non-image files are rejected client-side before they hit the wire; a non-vision model is rejected server-side with a clear message. Implemented with **zero new backend protocol**: the browser encodes each image as a `data:` URI and the existing `[img:…]` token path resolves it — `vision.rs` now accepts `data:<mime>;base64,…` tokens in addition to filesystem paths and URLs.

- Fixed the web UI todo panel showing empty item rows: each task's text was blank because the frontend wire type read a non-existent `content` field, while the backend serializes the description as `text`. The panel now renders the task text for every item.
- Added a 📎 clip button to the web UI composer for attaching/uploading images via a native file picker (multi-select), complementing the existing paste and drag-and-drop paths. All three routes share the same size/count validation and produce the same `[img:…]` tokens, so no backend changes were needed.
- `peakbot --web` (Phase 4): **remote access + browser auto-open.** The web UI can now listen beyond loopback via `--bind <host:port>` and is guarded by a shared secret from `--token <secret>` or the `PEAKBOT_WEB_TOKEN` env var (env preferred — keeps the secret out of shell history). When a token is set, every route (assets, `/commands`, `/ws`) is gated: the browser presents it once as `?token=…`, the server sets a `peakbot_token` cookie, and all later requests — including the WebSocket upgrade — authenticate via that cookie, so no token-threading code is needed on the frontend. Binding to a non-loopback address **without** a token is refused at startup, so an agent that can run shell commands can never be exposed to the network unauthenticated. On a local, non-SSH session `--web` now auto-opens your browser to the UI (loopback only; remote/SSH sessions just print the URL). Release binaries already embedded the SPA since Phase 0, so no extra release wiring was needed. (ETag/304 + pre-compressed static serving were considered and deliberately left out — the single-operator remote case loads the bundle once, so the added negotiation code isn't worth it.)
- `peakbot --web`: **sticky-session reliability fixes** (follow-up to #118). Fixed defects where the browser silently landed on a *fresh, empty* session instead of the one you meant. The conversation id in the URL (`?convo=`) is the single binding: a refresh, a reopened same-URL tab, or a shared link rejoins the same live session (so background processes started there are still there on reconnect), while a brand-new window with no `?convo=` starts a fresh conversation — the least-astonishing default. Resuming a conversation from the picker now **re-attaches** to it (sharing the live session if one exists, else resuming from disk) rather than issuing `/load` — so it no longer prints "Loaded conversation" for a session you're merely rejoining, and no longer clears that session's background processes. Opening a `?convo=<id>` link now actually restores the transcript — `AppState.conversation` was never populated, so the URL binding was dead; it is now mirrored on every conversation create/load, and the welcome banner no longer overlays a resumed transcript. No wire-protocol or config changes.
- `peakbot --web`: **sticky sessions that survive WebSocket disconnects** (issue #118). A conversation now rides in the URL (`?convo=<id>`), and a live agent session stays bound to it independently of any socket. A network blip, refresh, or reconnect re-attaches to the *same* running session — the transcript, todos, and stats are all still there (no more losing your session when the socket drops). Two tabs (or two browsers) on the same `?convo=` URL share one live session and see the same state in real time. The conversations picker now marks **active** sessions (bold + a green "live" dot) and offers a ✕ to kill one for everyone attached. Sessions that go idle with nobody connected are reaped after a configurable timeout — `web.session_ttl_secs` (default 1800 = 30 min) and `web.reaper_tick_secs` (default 60) in `config.yaml`. Teardown is always graceful (kills background PTY children cleanly). Internally, a per-conversation session registry replaces the previous one-session-per-socket model; a session's boot conversation is now initialised synchronously in `create_session` so its id is known the instant it exists.
